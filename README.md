# 展厅灯光提示联排演练器

纯前端演练器：导入一份 UTF-8 JSON 提示清单后，按数组顺序在各自截止时刻执行提示，模拟闭馆后灯光联排。针对“浏览器标签页降频导致定时回调延迟”的场景设计：所有截止时刻都由单调时钟的绝对时刻计算，延迟回调只会造成**集中处理**，不会把整段演练顺延。

技术栈：TypeScript + React + Vite，Vitest 单元测试，Playwright 端到端测试。

## 启动

### Docker Compose（推荐）

```bash
docker compose up --build web
```

打开 <http://localhost:8080>。宿主端口可用环境变量 `WEB_PORT` 覆盖：

```bash
WEB_PORT=3000 docker compose up --build web   # 打开 http://localhost:3000
```

### 一次性验收服务 verify

```bash
docker compose run --build --rm verify
```

`verify` 服务在含浏览器的镜像中依次执行 `npm run build`、Vitest 单元测试和 Playwright 端到端测试（Playwright 会启动 `vite preview` 并驱动真实浏览器覆盖计时链路），跑完即退出。

### 本地开发

```bash
npm install
npm run dev        # 开发服务器
npm run verify     # 构建 + Vitest + Playwright（需先 npx playwright install chromium）
```

## JSON 清单格式

页面通过“导入提示清单”读取 UTF-8 JSON 文件，顶层必须是**非空数组**，每项只能包含以下字段：

| 字段             | 要求                                       |
| ---------------- | ------------------------------------------ |
| `id`             | 字符串或数字，全清单内唯一（数字 `1` 与文本 `"1"` 视为同一 id），不能为空 |
| `label`          | 非空字符串（去除首尾空白后不能为空）       |
| `durationMs`     | 整数，范围 **100 ～ 600000**（该项时长，毫秒） |
| `maxLatenessMs`  | **可选**。出现时必须是 **0 ～ 600000 的整数**（该项可接受的最大回调迟到毫秒，`0` 表示零容忍）；省略则只记录迟到量，不做准时/超限判定 |
| `channelStart`   | **可选**。灯具起始通道，**1 ～ 512 的整数**；必须与 `channelCount` 同时出现或同时省略 |
| `channelCount`   | **可选**。占用通道数，**1 ～ 512 的整数**，且结束通道（`channelStart + channelCount - 1`）不得超过 **512**；必须与 `channelStart` 同时出现或同时省略 |
| `warningLeadMs`  | **可选**。到期预告提前量，**0 ～ 该项 `durationMs` 的整数**；省略则该提示不显示预告。引擎在“计划截止 − 预告时长”处把当前提示标为“即将到期”，此前标为“等待预告”，到达原截止时刻仍按既有规则结算 |

示例（见 `examples/cues.sample.json`、带阈值的 `examples/cues.lateness.sample.json`、带通道配接的 `examples/cues.channels.sample.json` 与带到期预告的 `examples/cues.warning.sample.json`）：

```json
[
  { "id": "open", "label": "开场主灯渐亮", "durationMs": 3000, "channelStart": 1, "channelCount": 16 },
  { "id": "spot", "label": "追光扫过中央展台", "durationMs": 5000, "maxLatenessMs": 500, "channelStart": 17, "channelCount": 8 },
  { "id": "finale", "label": "谢幕全场亮灯", "durationMs": 6000, "warningLeadMs": 1000 }
]
```

**任一项非法（含出现额外字段、`maxLatenessMs` 类型或范围非法、通道字段未成对出现或越界、`warningLeadMs` 非整数或不在 0 ～ 该项 `durationMs` 范围内）即整份拒绝**：页面就地显示错误原因（指出具体条目序号与字段名），当前已载入的有效数据与运行状态（含演练进度与暂停状态）保持不变。新旧字段可在同一份清单内混用。

**编码校验**：文件按严格 UTF-8 解码；包含无法解码的非法字节时整份拒绝并提示编码异常——乱码不会作为有效标签载入。标签中合法编码的替换字符（U+FFFD）属于正常内容，可正常载入。

## 计时语义

- **单调时钟**：截止时刻由 `performance.now()` 计算（引擎通过构造函数注入时钟，测试中以手动时钟精确驱动）。
- **绝对截止，不靠递减 tick**：第 n 项的计划截止时刻 = 启动时刻 + 前 n 项时长累加。回调迟到不会改变后续项的截止时刻。
- **暂停 / 恢复**：暂停先结算所有已到期但尚未收到回调的项（保留各自原截止时刻，按暂停时刻记录真实迟到并判定），再冻结第一个尚未到期项的剩余毫秒数（若结算后全部到期则直接完成）；恢复时以该余量建立新的绝对截止时刻，后续项依次累加。
- **延迟回调**：回调若因标签页降频迟到并跨过多项，引擎按各自截止时刻依次把每项记入轨迹（实际处理时刻为回调真实到达时刻），并把“当前应执行项”直接推进到第一个尚未到期的项。
- **到期预告（warningLeadMs）**：为某项配置 `warningLeadMs` 后，引擎按单调时钟在「计划截止 − 预告时长」这一**绝对预告点**把当前提示标为“即将到期”，预告点之前标为“等待预告”，页面在当前提示旁展示对应状态与剩余毫秒（等待预告时显示距预告点，即将到期时显示距截止）；预告只作标记，到达原截止时刻仍按既有规则结算。预告点与截止点都是绝对时刻：延迟回调跨过预告点时按当前绝对时刻直接呈现“即将到期”（不补发预告），跨过截止点时照常结算，二者都**不改写后续截止时间**。一次回调可同时跨过预告点与截止点。暂停时预告进度随剩余毫秒一并冻结，恢复后以冻结余量重建预告边界（新预告点 = 恢复时刻 + 冻结余量 − 预告时长）。`warningLeadMs` 为 `0` 时预告点即截止点，不改变结算时刻；未配置该字段的旧清单不显示任何预告，迟到、跳过、通道检查与完成轨迹保持原表现。
- **人工跳过**：进行中可跳过当前提示——先按当前单调时刻结算所有已到期但尚未收到回调的项（记为“到期处理”），再把首个尚未到期项记为“人工跳过”：保留原计划截止与操作时刻，但不计算迟到量、不参与迟到判定与超限汇总；随后沿原绝对时间线等待下一项，不重排清单、不延长总计划。跳过末项（或结算后全部到期）则立即完成。
- **迟到判定**：每项处理时以「实际处理时刻 − 计划截止时刻」计算迟到量（毫秒）。配置了 `maxLatenessMs` 的项独立判定——迟到量不超过阈值为“准时”，超过为“超限”，**即使一次延迟跨过多项，各项仍按各自阈值独立判断**；阈值包含边界（迟到量恰等于阈值算准时）。未配置阈值的旧项只记录迟到量，不参与判级与汇总。判定不改变绝对截止、暂停/恢复与完成条件。
- **通道占用检查**：清单载入时，对所有配置了 `channelStart`/`channelCount` 的提示按闭区间 `[channelStart, channelStart + channelCount - 1]` 两两比较——区间相交（含端点相接）即为**冲突**，冲突双方互相列出对方标签与重叠范围；无重叠的已配置项标为**可用**；未配置通道的旧项标为**未配接**，不参与比较。检查结果进入引擎快照，显示在清单表格与完成轨迹中（含“冲突 N 项”汇总），但**只作联排提示**，不改变开始、暂停、恢复、绝对截止、迟到判定与完成条件；未配接的旧格式清单仍可直接演练。
- **错误处理**：未载入时启动、状态不符的重复操作（重复开始、未暂停时继续等）均就地报错，且不改变任何状态；进行中或已暂停时导入新清单会被拒绝，提示分别明确反映“进行中”或“已暂停”状态。
- **完成展示**：最后一项处理后界面稳定显示“已完成”，并列出全部提示的计划截止时间、实际处理时间、处理类型（到期处理 / 人工跳过）、迟到量与判定；表格上方汇总“超限 N 项”（未配置阈值的项不计入），旧格式清单各判定格显示“未设标准”——可直观看到一次长延迟虽造成集中处理，却没有延长整段演练。人工跳过项的判定格写明“人工跳过（不计算迟到，不参与判定）”；末项为人工跳过时，完成摘要把提前点击的操作时刻明确标注为“人工跳过时刻”，而非实际处理时刻。
